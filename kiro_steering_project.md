# Spectroscopy Assistant: project rules
(Place this file at `.kiro/steering/project.md` in the repo.)

## Purpose
Help an AFS expert make a FIRST technical assessment of a new customer enquiry on in-line spectroscopy.
The assistant supports the expert. It does not replace them and does not give final configurations.

## Knowledge base (main source)
- `knowledge/` holds page-tagged text built by `ingest.py` from the supplied AFS materials:
  S01 (19 pages), S02 (20 slides, image-based: use the committed vision notes), S03, S04, S05, plus
  `AFS_method_comparison_table.xlsx` (transcription of S01 Table 1, page 6) and the fiber-family table.
- Cite as `S01 p.10` (1-based PDF page, title page = 1). For slides, `S02 p.13` = slide 13.
- AFS materials are the main source. Any external source must be cited with the quoted passage and link.
- S03 and S04 are research papers (proof of concept / laboratory). S05 and S06 are business context,
  not technical evidence. Keep a `scope` tag per source and do not cite beyond it.

## Output contract
- Every answer is JSON that validates against `schema/assessment.schema.json`, then is rendered for humans.
- Keep four things visibly separate: client facts, sourced claims, assumptions, proposed experiments.

## Hard rules (applied in prompts AND checked in code)
1. Anything the client did not state is unknown: ask about it or list it as an explicit assumption.
2. Never invent measured results, accuracy, detection limits, response times, fiber lengths,
   product codes, prices or component ratings that no source supports.
3. A published application is a reason to test a method, not proof it will work for this customer.
4. Decision status is one of: provisional_assessment, insufficient_information, outside_supported_scope.
   "insufficient_information" is a good answer when the facts cannot justify a method choice.
5. A nominal method range is not the range of a specific instrument, fiber or probe.
   Raman: state laser excitation (nm) separately from Raman shift (cm-1). wavelength_um = 10000 / wavenumber.
6. If AFS sources disagree, prefer explicit text over figure labels and report it in `source_conflicts`.
7. Acceptance targets for go / no-go come from the client; never invent them.

## Pipeline
ingest -> extract facts (stated / unknown / assumed) -> assess (schema-constrained LLM call)
-> verify in code (citations exist, quotes appear on the cited page, fiber/range compatibility,
numbers not found in sources or enquiry are flagged, status consistent with open unknowns)
-> one repair pass -> render.

## Repo hygiene (important for the evaluation)
- No scenario-specific text, rules or examples in prompts or code. Generic behaviour only.
- Develop and tune on D01 to D08. Final scenarios are run only via `run_scenarios.py`.
- Final outputs are generated by the assistant, committed unedited, and never hand-corrected.
- A test (`tests/test_no_leakage.py`) fails if prompts or rule files contain distinctive phrases
  from the final-evaluation file.

## Tests
- Schema validation on every output.
- Citation check unit tests (page exists, quote present).
- Range check unit tests (unit conversion, fiber-family limits).
- Regression run on D01 to D08 before each commit.
