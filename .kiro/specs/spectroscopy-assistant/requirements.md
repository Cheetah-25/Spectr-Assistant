# Requirements — Spectroscopy Assistant

## Introduction

The Spectroscopy Assistant helps an AFS (Art Photonics / in-line spectroscopy) expert make a
**first** technical assessment of a new customer enquiry about in-line fiber-optic spectroscopy.
It supports the expert; it does not replace them and does not produce final configurations.

The assistant ingests a fixed set of AFS source materials into a page-tagged knowledge base, then
for each enquiry extracts the stated facts/unknowns/assumptions and produces a JSON assessment that
validates against `schema/assessment.schema.json`. Every output is verified by plain-Python checks
(citations, quotes, spectral ranges, unsupported numbers, status consistency) and repaired once if
checks fail. Results are viewable in a Streamlit UI and runnable in batch over a scenario file.

The governing rules are in `.kiro/steering/project.md` (the committed `kiro_steering_project.md`).
This document restates them as testable requirements.

### Key constraints (global)
- **No scenario-specific text** in prompts, rules, or code. Only generic behaviour.
- **Schema limits (brevity, rule 8):** `schema/assessment.schema.json` caps `clarification_questions`
  at `maxItems: 5`, `recommendations` at `maxItems: 3`, and each recommendation `rationale` at
  `maxLength: 300`. Tests assert these limits.
- LLM provider and API key come from **environment variables**; no keys in code.
- Develop/tune on `D01`–`D08` only. Final-evaluation scenarios are **not** in this repo and must
  never be read, referenced, or used to shape prompts/rules.
- Final outputs are generated by the assistant and committed **unedited**; never hand-corrected.
- Ship `requirements.txt` and a README with setup + run instructions.

### Target repo layout (to be created)
```
materials/   S01–S05 PDFs + AFS_method_comparison_table.xlsx   (knowledge sources)
data/        dev_scenarios.json, fiber_families.json
schema/      assessment.schema.json
knowledge/   page-tagged KB written by ingest.py (committed)
outputs/     per-case .json + .md written by run_scenarios.py
tests/       pytest suite
ingest.py  assess.py  verify.py  run_scenarios.py  app.py
requirements.txt  README.md
.kiro/steering/project.md
```
Note: the repo currently stores these files flat at the root. Reorganizing into the layout above is
part of this work (Requirement 10).

## Requirement 1 — Knowledge base ingestion (`ingest.py`)

**User story:** As a developer, I want the AFS materials turned into a page-tagged knowledge base, so
that the assistant can cite exact sources and pages and code can verify those citations.

### Acceptance criteria
1. WHEN `ingest.py` runs THEN it SHALL read each text PDF (`S01`, `S03`, `S04`, `S05`) and write one
   knowledge entry per page, each tagged with `source_id` and a **1-based** page number (title page = 1).
2. WHEN emitting a citation locator for a page THEN the format SHALL be `S01 p.10` style
   (`S<nn> p.<1-based-page>`); for `S02` the page number SHALL mean the slide number (`S02 p.13` = slide 13).
3. WHEN ingesting `S02` (image-based, 20 slides) THEN `ingest.py` SHALL **load the committed
   `knowledge/S02_slides.json`** — a JSON object with a `provenance` string and a `slides` array
   (`slide_number`, `title`, `description`) — and write each slide into the knowledge base tagged
   `S02 p.N` with scope `"AFS slides"`. There SHALL be **no vision pass and no `--force-vision`**;
   the slide notes are authored and committed, not model-generated.
4. WHEN ingesting `AFS_method_comparison_table.xlsx` THEN `ingest.py` SHALL load it as **structured
   rows** (the transcription of S01 Table 1, page 6) and SHALL keep its notes sheet.
5. WHEN ingestion completes THEN the KB SHALL carry a `scope` tag per source
   (S01/S02 = AFS technical material; S03/S04 = research paper (proof of concept / lab);
   S05/S06 = business context, not technical evidence) and a KB version identifier.
6. WHEN the KB is written THEN each entry's text SHALL be stored so that a later exact substring check
   of a short `quote` against the cited page can succeed (whitespace-normalized comparison is allowed).
7. IF a required source material file is missing THEN `ingest.py` SHALL fail with a clear error naming
   the missing file rather than writing a partial KB silently.

## Requirement 2 — Fact extraction and schema-constrained assessment (`assess.py`)

**User story:** As an AFS expert, I want each enquiry turned into a structured assessment that keeps
client facts, sourced claims, assumptions and proposed experiments separate, so I can review it quickly.

### Acceptance criteria
1. WHEN given an enquiry THEN `assess.py` SHALL first extract **stated facts**, **unknowns** (with
   `why_it_matters`), and **assumptions**, deriving stated facts only from the enquiry text.
2. WHEN producing the assessment THEN `assess.py` SHALL make a **schema-constrained LLM call** whose
   prompt contains the **whole page-tagged knowledge base** and SHALL return JSON that validates
   against `schema/assessment.schema.json`.
3. WHEN the output or verification checks fail THEN `assess.py` SHALL **retry exactly once**, feeding
   the specific verification errors back into the repair prompt.
4. WHEN building any prompt THEN it SHALL contain **no scenario-specific wording** and SHALL encode the
   steering "hard rules" (1–11) generically: unknowns must be asked or assumed; never invent measured
   results/limits/response-times/fiber-lengths/product-codes/prices/ratings; a published application
   justifies testing, not success; `decision_status` ∈
   {`provisional_assessment`,`insufficient_information`,`outside_supported_scope`}; Raman excitation nm
   stated separately from Raman shift cm⁻¹; prefer explicit text over figure labels for conflicts;
   acceptance/go-no-go targets come from the client; **be concise** (rule 8: ≤5 clarification
   questions, ≤3 recommendations, 1–2 sentences per rationale, short bullets, no marketing language);
   **frame every output as a first assessment for AFS-expert review** with hedged wording such as
   "worth testing" / "to be confirmed by AFS" and never as a final decision/approval/configuration
   (rule 9); **never state prices/costs/product codes/delivery times/component ratings not in the
   sources**, and if asked, say they are outside this assessment and refer to AFS (rule 10); **never
   quote research results S03/S04 as proof of process or clinical readiness** (rule 11).
4a. WHEN the facts cannot justify a method choice THEN `insufficient_information` SHALL be treated as a
   valid, acceptable outcome (not an error).
5. WHEN a response is returned THEN `assess.py` SHALL fill `meta.model`, `meta.kb_version`,
   `meta.generated_at`, and leave `meta.verification` for `verify.py` to populate.
6. WHEN the LLM provider/key is needed THEN it SHALL be read from environment variables; absence SHALL
   produce a clear error and SHALL NOT crash with a traceback that leaks internals.

## Requirement 3 — Code-only verification (`verify.py`)

**User story:** As a reviewer, I want deterministic Python checks (no LLM) that catch hallucinated
citations, numbers and ranges, so I can trust the separation between sourced and invented content.

### Acceptance criteria
1. WHEN verifying THEN `verify.py` SHALL validate the assessment against the JSON schema and report
   `citations_ok`, `range_check_ok`, `unsupported_numbers`, and `warnings` in `meta.verification`.
2. WHEN a citation is present THEN `verify.py` SHALL confirm its `source_id` exists and its `page`
   exists for that source (slide number for S02), flagging any that do not.
3. WHEN a citation has a `quote` THEN `verify.py` SHALL confirm that quote appears on the cited page
   (whitespace-normalized substring match); otherwise flag it.
4. WHEN spectral ranges are present THEN `verify.py` SHALL check them against `fiber_families.json`,
   applying `wavelength_um = 10000 / wavenumber_cm-1` to convert cm⁻¹ ranges, and converting nm↔µm, so
   that a method range claimed to be carried by a named fiber family lies within that family's
   transmission window; mismatches are flagged.
5. WHEN numbers appear in the answer text THEN any number that appears **neither** in the knowledge
   base **nor** in the enquiry SHALL be listed in `unsupported_numbers` (with sensible normalization of
   units/formatting and ignoring structural values such as `priority` indices and schema enums).
6. WHEN there are open unknowns that block a method choice THEN `verify.py` SHALL check that
   `decision_status` is consistent (e.g. not `provisional_assessment` with a confident primary
   recommendation while blocking unknowns are unresolved) and warn on inconsistency.
7. WHEN the output contains a **price, cost, product code, delivery time or component rating** that
   does not appear in the knowledge base THEN `verify.py` SHALL flag it (enforces steering rule 10).
8. WHEN a citation to **S03 or S04** is used to support a **process-readiness or clinical-readiness**
   claim THEN `verify.py` SHALL flag it (enforces steering rule 11).
9. WHEN all checks pass THEN `verify.py` SHALL return a result object that callers can use to decide
   whether to trigger the single repair pass; `verify.py` SHALL perform **no LLM calls**.

## Requirement 4 — Batch runner (`run_scenarios.py`)

**User story:** As a developer/evaluator, I want to run a whole scenario file through the pipeline and
get reproducible artifacts, so results can be committed unedited.

### Acceptance criteria
1. WHEN given a scenario file path THEN `run_scenarios.py` SHALL run each case through
   extract → assess → verify → one repair pass → render.
2. WHEN a case completes THEN it SHALL write exactly one `.json` and one `.md` per case into
   `outputs/`, named by `case_id`.
3. WHEN writing outputs THEN they SHALL be written **unedited** (no post-hoc hand correction) and the
   `.md` SHALL be a human-readable rendering of the same assessment.
4. WHEN the runner reads scenarios THEN it SHALL use only `enquiry` and `id`/`title`; it SHALL NOT feed
   `useful_sources` (or any other developer hint) into the assistant.
5. WHEN run over `data/dev_scenarios.json` THEN it SHALL process `D01`–`D08` without manual steps.

## Requirement 5 — Streamlit UI (`app.py`)

**User story:** As an AFS expert, I want a simple UI to enter an enquiry or pick an example and see a
clear summary plus the full reasoning, so I can review an assessment at a glance.

### Acceptance criteria
1. WHEN the app loads THEN it SHALL offer a free-text input box and an example picker populated from
   the development scenarios.
2. WHEN an assessment is produced THEN a **short summary view** SHALL show `decision_status`, the top
   clarification questions, and the recommendation(s); details go in "show reasoning", not the summary.
3. WHEN the user expands **"show reasoning"** THEN it SHALL show stated facts, assumptions, citations,
   source conflicts, and the verification result.
4a. WHEN any report is rendered THEN it SHALL begin with the exact line: "First assessment to support
    an AFS expert; not a final recommendation." (enforces steering rule 9 / Output contract).
4. WHEN provider/key env vars are missing THEN the app SHALL show a clear, non-crashing message.

## Requirement 6 — Tests (`tests/`)

**User story:** As a maintainer, I want tests that lock in the contract and guard against leakage, so
regressions and accidental scenario-specific content are caught.

### Acceptance criteria
1. WHEN tests run THEN there SHALL be a **schema validation** test that fails on an invalid assessment
   and passes on a valid one.
2. WHEN tests run THEN there SHALL be a **citation check** test (page exists; quote present on page).
3. WHEN tests run THEN there SHALL be a **range check** test covering the cm⁻¹→µm conversion and
   fiber-family limits.
4. WHEN tests run THEN there SHALL be a **leakage test** (`tests/test_no_leakage.py`) that fails if any
   prompt or rule file contains scenario-specific/distinctive phrases.
5. WHEN tests run THEN they SHALL NOT require network/LLM access (LLM is mocked or the checks are
   exercised against fixtures).

---

## Requirement 7 — Prompt & rule hygiene (no leakage, generic behaviour)

**User story:** As an evaluator, I want assurance that the system behaves generically, so results
reflect capability and not memorized scenario answers.

### Acceptance criteria
1. WHEN prompts/rules are authored THEN they SHALL contain no customer/scenario-specific nouns,
   numbers, or phrasing from any scenario (dev or final).
2. WHEN hard rules are expressed THEN they SHALL be generic statements about how to reason, matching
   `.kiro/steering/project.md`.
3. WHEN final-evaluation scenarios are referenced THEN the code SHALL only accept them through
   `run_scenarios.py` at run time and SHALL never embed their text.

---

## Requirement 8 — Configuration & provider abstraction

**User story:** As an operator, I want to choose the LLM provider and supply keys via environment, so
the app is portable and secret-safe.

### Acceptance criteria
1. WHEN the app/pipeline starts THEN provider selection and API key SHALL be read from environment
   variables (documented in the README).
2. WHEN a text completion is needed (fact extraction, assessment) THEN the provider layer SHALL
   support it via configuration. S02 ingestion requires **no vision call** (the slide notes are
   committed), though the provider layer MAY expose a vision method for future use.
3. WHEN no key is set THEN non-LLM paths (verify, tests, rendering existing outputs) SHALL still work.

---

## Requirement 9 — Reproducibility & artifacts

**User story:** As an evaluator, I want committed, reproducible artifacts, so the KB and dev outputs
can be reviewed without re-running the LLM.

### Acceptance criteria
1. WHEN `ingest.py` has run THEN the `knowledge/` files (including the S02 vision notes and the xlsx
   rows) SHALL be committable and reused by `assess.py` without re-invoking vision.
2. WHEN `run_scenarios.py` has run on `D01`–`D08` THEN `outputs/` SHALL contain the generated
   `.json`/`.md` committed unedited.
3. WHEN outputs are generated THEN `meta.kb_version` and `meta.generated_at` SHALL make the run
   traceable.

---

## Requirement 10 — Repository reorganization

**User story:** As a developer, I want the repo to match the documented layout, so paths referenced in
the steering file and code are correct.

### Acceptance criteria
1. WHEN the project is set up THEN the PDFs and xlsx SHALL live under `materials/`, the scenario/fiber
   JSON under `data/`, and the schema under `schema/`, using `git mv` to preserve history.
2. WHEN steering is finalized THEN `.kiro/steering/project.md` SHALL hold the project rules (from
   `kiro_steering_project.md`).
3. WHEN code references inputs THEN it SHALL use the new paths; no code SHALL depend on the old flat
   layout.
